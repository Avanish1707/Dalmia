# ALCON Surveillance Backend

Dalmia VMS is a Flask surveillance service. Its active camera path reads NVR
RTSP streams, runs only InsightFace face detection and ArcFace recognition,
sends confirmed unknown-face alerts by email, and provides an authenticated
browser dashboard with annotated camera streams.

The active camera behavior lives in `alcon_stream_new.py`; other detector and
event modules remain available in the repository but are not used by the
current face-only camera path.

## Run

Use the project virtual environment on Windows:

```powershell
.\venv\Scripts\python.exe app.py
```

The server listens on `0.0.0.0:5000` by default. `python app.py` imports the
`main()` entry point from `alcon_stream_new.py`, initializes email delivery
when configured, loads the face model and database, starts enabled camera
workers, and runs Flask-Socket.IO with the threaded async mode.

## Current Architecture

```text
app.py
  -> alcon_stream_new.main()
		 -> bounded asynchronous email-alert worker (when configured)
		 -> camera configuration and state initialization
		 -> one shared InsightFace buffalo_s instance with only face detection
		    and ArcFace
		    w600k_mbf recognition for every enabled camera worker
		 -> registered-face cache and auth accounts
		 -> CameraManager
				-> one camera_worker thread per enabled camera
					  -> RTSP read/reconnect
					  -> face detection and known/unknown recognition only
					  -> confirmed unknown-face email queue
					  -> annotated-frame buffer
  -> authenticated dashboard and HTTP MJPEG streams
```

`app.py` is already a small launcher. `camera/manager.py` owns worker
lifecycle. Other detector and event modules remain in the repository but are
not initialized or called by the current face-only camera path.

## Configuration

Camera definitions remain in `config/cameras.json`. Each item contains the
camera ID, display name, NVR address, KPI, enabled flag, channel, and subtype.
CAM001 uses the `known_unknown` KPI for annotated known/unknown person detection;
vehicle inference is enabled only for cameras configured with the `vehicle` KPI.
InsightFace face detection and recognition are pinned to CPU, regardless of GPU availability.
The shared `buffalo_s` face pipeline requires its `w600k_mbf.onnx` ArcFace
recognition model and is used by all enabled camera workers.
Known-face embeddings are model-specific; after changing from `buffalo_l`,
re-register known people so their stored embeddings are generated by
`buffalo_s` before relying on known/unknown classification.
An optional `RTSP_URL` or `rtsp_url` is an explicit endpoint override and takes
precedence over the NVR/channel/subtype fallback. URL credentials in the
configuration are discarded; the worker uses `ALCON_PASSWORD` from the
environment with the existing `admin` username. Do not commit credentials.

Subtypes follow the camera configuration contract: `1` is main stream
(`/Streaming/Channels/101` for channel 1) and `2` is substream
(`/Streaming/Channels/102`). A configured URL path overrides that mapping.
Environment overrides are supported for each camera:

```env
ENABLED_CAMERAS=CAM001,CAM003
CAM001_NVR_IP=192.168.191.40
CAM001_CHANNEL=1
CAM001_SUBTYPE=1
CAM001_ENABLED=true
# Set ALCON_PASSWORD out of band; never commit its value.
```

`ENABLED_CAMERAS=ALL` enables every configured camera. Invalid camera IDs are
rejected. `config/cameras.py` is now the owner of this loading behavior.

### Windows RTSP diagnostics

Run these checks from PowerShell on the Dalmia host. A TCP success only confirms
reachability to the RTSP port; it does not validate credentials or the stream
path.

```powershell
Test-NetConnection 192.168.191.40 -Port 554
Get-Command ffmpeg, ffprobe -ErrorAction SilentlyContinue
```

If FFmpeg/FFprobe are missing, install a Windows FFmpeg build (for example,
`winget install --id Gyan.FFmpeg.Shared --exact`), open a new PowerShell
session, and verify with:

```powershell
ffmpeg -version
ffprobe -version
```

If either command is still not found, add the FFmpeg `bin` directory (the
directory containing both executables) to the user or system `PATH`, then
restart PowerShell. Do not download executables from untrusted mirrors.

To probe both candidate streams over RTSP/TCP, enter the password only at the
secure prompt below. FFprobe debug output can echo a URL, so the script masks
URL credentials and query strings before displaying the captured response.
The URL is necessarily passed to the local FFprobe process; run this only on a
trusted host and do not paste unfiltered output into logs or tickets.

```powershell
$secure = Read-Host 'NVR password' -AsSecureString
$ptr = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($secure)
try {
    $password = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($ptr)
} finally {
    [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($ptr)
}
$escapedPassword = [Uri]::EscapeDataString($password)
foreach ($path in '101', '102') {
    $url = "rtsp://admin:$escapedPassword@192.168.191.40:554/Streaming/Channels/$path"
    "=== stream $path ==="
    $output = & ffprobe -v debug -rtsp_transport tcp -timeout 10000000 `
        -select_streams v:0 -show_entries stream=codec_name,profile,width,height `
        -of default=noprint_wrappers=1 $url 2>&1
    $exitCode = $LASTEXITCODE
    $output | ForEach-Object {
        "$_" -replace '(?i)(rtsp://[^:/\s]+:)[^@/\s]+@', '$1***@' `
            -replace '(?i)(rtsp://[^?\s]+)\?[^\s]+', '$1?<redacted>'
    }
    "ffprobe exit code: $exitCode"
}
$password = $null
$escapedPassword = $null
$url = $null
```

Interpret the results by stage: TCP timeout/refusal indicates routing,
firewall, or RTSP service reachability; RTSP `401` indicates authentication;
`404` on `DESCRIBE`/`OPTIONS` usually indicates an invalid endpoint/path or an
unsupported method; `SETUP` `500` means the NVR rejected stream setup after
reaching the endpoint and warrants checking the channel/substream configuration
and NVR firmware/logs. A successful RTSP negotiation followed by codec or
parameter errors points to stream encoding/codec negotiation. Compare the two
paths using the same credentials and TCP transport before changing the
application configuration. `ffprobe` not being found is a local tool/PATH
issue, not evidence about RTSP validity.

The active ROI values are in `roi/camera_rois.py`. `CAMERA_ROIS` contains one
independent entry for every configured camera. Edit only the camera you want:

```python
CAMERA_ROIS["CAM001"]["points"] = np.array([
	[0.10, 1.00],
	[0.12, 0.82],
	# ... normalized [x, y] points ...
], dtype=np.float32)

CAMERA_ROIS["CAM001"]["vehicle"] = {
	"points": np.array([
		[0.00, 0.35],
		[1.00, 0.35],
		[1.00, 0.70],
		[0.00, 0.70],
	], dtype=np.float32),
}
```

`get_camera_roi(camera_id)` returns a copy, and the worker passes its own
camera ID into every ROI check. Changing `CAM001` therefore cannot modify
`CAM002`. The initial values are the exact existing production polygon and
vehicle polygon. Vehicle detection checks the box center and bottom-center
against `vehicle.points` using point-in-polygon; detections outside the
polygon are ignored.

Registration quality is configured separately from live recognition. The
backend keeps the existing `image1` through `image5` contract but rejects
faces that are too small, too close to the image edge, below the registration
detection score, blurry, non-finite, or not 512-dimensional. The settings are
`REGISTRATION_MIN_FACE_WIDTH_RATIO`, `REGISTRATION_MIN_FACE_HEIGHT_RATIO`,
`REGISTRATION_MIN_FACE_PIXELS`, `REGISTRATION_FACE_EDGE_MARGIN`,
`REGISTRATION_MIN_DET_SCORE`, `REGISTRATION_MIN_BLUR_SCORE`, and
`REGISTRATION_IDENTICAL_SIMILARITY`. None changes live recognition.

Registration diagnostics are printed without embedding values. For each
upload they include decoded byte count and shape, EXIF orientation, active
ONNX session providers, detector size and threshold, face count, face boxes,
and detection scores. Test with Postman using `multipart/form-data` and the
unchanged fields `gate_no`, `employee_name`, `designation`, optional
`employee_id`, and exactly one file for each of `image1` through `image5`.
The response remains `201` with `success`, `registration_id`, and
`images_registered: 5` after all five images pass.

If the primary registration detector returns zero faces, the backend retries
the same Buffalo_L detector once at `REGISTRATION_FALLBACK_DET_SIZE` (default
`1200`). The retry runs under the existing shared face/GPU lock and the live
detector is restored to `DET_SIZE` and `DET_THRESH` immediately afterward.
Zero faces still fail, and multiple faces still fail the existing
exactly-one-face rule.

## End-to-End Workflow

### Startup

1. `app.py` imports `main` and calls it.
2. `.env` is loaded and paths are resolved relative to the project directory.
3. SMTP settings are validated without logging values; a bounded email worker
   starts when valid, while invalid settings are logged and leave inference
   available without the email service. Firebase is not initialized as a
   prerequisite for detection alerts.
4. Enabled camera records are loaded and camera state dictionaries are created.
5. H.264 configuration is requested from each enabled NVR using HTTP digest auth.
6. InsightFace `buffalo_s` is loaded with only its face detection and ArcFace
	`w600k_mbf.onnx` recognition modules, then shared by enabled cameras.
7. Other detector models and `DetectionEventManager` are not initialized.
8. PostgreSQL connection and application schemas are checked through the
   configured database connection.
9. Registered face embeddings and metadata are loaded into the live cache.
10. Default admin/user accounts are inserted only when absent.
11. `CameraManager` starts one daemon worker per enabled camera.
12. Flask-SocketIO starts and signal handlers stop workers on shutdown.

### Per-camera frame processing

Each worker repeatedly opens its configured RTSP URL and reconnects after
repeated read failures. Every configured processing frame runs InsightFace
detection and recognition only. Unknown faces must pass the face score gate
and appear in two detections of the same spatial track; the worker then saves
annotated evidence and submits one email. It does not run YOLO, ROI tracking,
database event persistence, or Socket.IO detection alerts. Annotated frames
remain available through the dashboard's MJPEG stream.

### Recognition

Registration requires exactly five uploads named `image1` through `image5`.
Each image must contain exactly one InsightFace detection. Each embedding is
normalized and stored independently in `registered_face_embeddings`.
Recognition compares the live normalized embedding against every template,
keeps the best score per person, ranks people globally, and applies the
existing threshold and margin. It does not average templates for live
recognition. `known_embeddings` remains as a legacy compatibility cache.

### Event and alert workflow

The active camera-worker path runs only InsightFace face detection and ArcFace
recognition. Person/vehicle/PPE/fall/smoke-fire/object-theft model
initialization and event tracking are disabled. Each face is associated across
two inference frames; a validated unknown face is emailed directly and is not
sent through Socket.IO or the detection-event manager.

#### Why a face may not become an unknown-person detection

InsightFace runs on each camera frame without a YOLO person detector or ROI
gate. Only unusable bounding boxes (non-finite, empty, or entirely outside
the frame) and detections below
`FACE_RECOGNITION_MIN_DET_SCORE` (default `0.40`) are rejected. An unknown
must also meet `UNKNOWN_FACE_MIN_SCORE` (default `0.40`) and be confirmed on
two inference frames before email is attempted.

The recognition matcher deliberately holds borderline matches as `PENDING`:
candidate similarity at/above `RECOGNITION_CANDIDATE_THRESHOLD` (default
`0.43`) that fails the known threshold (`0.50`) or margin (`0.05`) is not
emailed as unknown. This avoids alerting on a possible registered person.
Follow `[FACE-ONLY][DETECT]`, `[FACE-ONLY][REJECT]`,
`[FACE-ONLY][IDENTITY]`, and `[FACE-ONLY][EMAIL]` logs to find the exact
decision stage for each camera.

Unknown-person email is queued on the first detected unknown face that passes
the configured face-score threshold. A track is emailed at most once while it
remains present; eligibility, evidence creation, queueing, and SMTP delivery
are logged separately.
Configure
`MAIL_HOST`, `MAIL_PORT`, `MAIL_FROM`, `ALERT_EMAIL_TO`, and the required
transport/authentication values in the deployment environment. Startup logs
field presence only (never values); if mail configuration is invalid, camera
inference and Flask remain available while email jobs are rejected with a
clear service-unavailable response. `stage=queue result=failed` means the
event was not accepted by the queue. `[EMAIL][DELIVERY] stage=attempt`
confirms SMTP delivery began. Follow the same `event_id` or `correlation_id`
through `stage=message_build`, `stage=smtp_connect`, `stage=starttls`,
`stage=authentication`, and each `stage=recipient_submit` entry to identify
the first failed step; use the `attempt` field to distinguish retries. Disabled
TLS or authentication is logged as skipped.
Recipient addresses and credentials are not included in these stage logs.
`stage=complete result=failed` reports the sanitized error, while
`stage=smtp_submission result=accepted` means the configured SMTP server
accepted the submission, not that delivery to the recipient's inbox was
verified.

Only confirmed unknown-face detections from the camera worker are sent through
the detection email queue. They do not emit `face_alert` or
`detection_event` Socket.IO messages. Evidence images are attached when
available. SMTP failures retry a bounded number of times and do not interrupt
face inference. Firebase/FCM registration routes remain for mobile-client
compatibility but are not used for unknown-face email alerts.

### Browser dashboard and email setup

Set `FLASK_SECRET_KEY` to a long random secret before exposing the dashboard.
The dashboard login uses existing `admin`/`user` credentials from
`auth_accounts`; the associated video feed requires the same browser session.
Set `SESSION_COOKIE_SECURE=true` when served through HTTPS. Open
`http://<server-host>:5000/dashboard` (or the HTTPS equivalent), sign in, and
the page loads only enabled cameras from `/api/cameras`. Each feed uses
`/video_feed/<camera_id>` and reconnects automatically through the browser's
MJPEG image handling. The dashboard polls status independently so one failed
camera does not block other feeds.

To enable SMTP alert delivery, configure `MAIL_HOST`, `MAIL_PORT`, `MAIL_FROM`,
and comma-separated `ALERT_EMAIL_TO`. `MAIL_USERNAME` and `MAIL_PASSWORD` must
both be set for authenticated SMTP. For Gmail, use a Google App Password,
not the account's regular password. Choose exactly one of
`MAIL_USE_TLS` (STARTTLS) or `MAIL_USE_SSL` for the configured provider.
Missing, partial, or invalid settings are reported safely at startup and keep
the email queue unavailable without stopping camera inference.
`POST /api/test-email` (or its backward-compatible `/api/test-notification`
alias) requires an authenticated dashboard session and returns `202` only
when the latest default-camera frame's test email has been queued. The response
includes a correlation ID for tracing the SMTP attempt. Do not use real SMTP
credentials in tests.

For deployment, install the existing requirements, set PostgreSQL, camera,
dashboard-secret, and SMTP environment values, then restart the service behind
the existing HTTPS reverse proxy. Confirm the dashboard, a known camera feed,
and the `GET /api/detections` response before routing users to the updated
release. No database migration is introduced. To roll back, stop the service
and restore the previous application release; keep PostgreSQL data untouched.
Email and dashboard environment variables can remain configured but will not
be consumed by the restored application version.

## Refactor Status and Migration Map

The completed safe phase is configuration and ROI ownership:

- `config/cameras.py` owns camera JSON parsing and enabled-camera selection.
- `roi/camera_rois.py` owns the exact active person and vehicle ROI values.
- `alcon_stream_new.py` imports those values instead of defining duplicates.
- Existing callers and API behavior remain unchanged.

The next migrations should proceed in this order:

1. Introduce `state/runtime_state.py` and move mutable dictionaries as one
	object, while retaining compatibility aliases for tests and callers.
2. Move the single GPU lock and safe inference wrappers to `detection/gpu.py`.
3. Move database connection/schema helpers and registration SQL into
	`database/connection.py`, `database/persons.py`, and `database/embeddings.py`.
4. Move face detection, cache, recognition, and identity tracking as units;
	each must receive the same state and model objects.
5. Move person/vehicle detection and vehicle tracking without changing model
	arguments or thresholds.
6. Move the worker body to `camera/worker.py`; keep RTSP ownership separate.
7. Move event/alert and Firebase/Socket.IO services.
8. Move routes into an API blueprint only after an automated endpoint map
	comparison passes.
9. Reduce `alcon_stream_new.py` to application assembly and shutdown.

At every step, copy or re-export first, validate imports and behavior, then
remove the old definition. Never instantiate models per worker and never make
separate cache or GPU-lock objects in different modules.

## Circular Import Risks

The main risk is a route module importing the worker while the worker imports
route globals. The intended dependency direction is:

```text
config -> database/state/utils -> detection/face/services
		 -> camera worker -> camera manager -> API -> app
```

Application assembly should pass model, state, socket, database, and event
manager references downward. Mutable process state should be accessed through
one module object, not copied with reassignment-prone `from module import
value` imports.
